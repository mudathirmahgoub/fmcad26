# Effect of the user-supplied nonnegativity change — full sequential rerun

2026-07-29. Baseline: `comparison_before_nonneg.csv` (full sequential run of
2026-07-27, solver-assumed nonnegativity). New run: `comparison.csv`, all six
configurations x 509 benchmarks, strictly sequential (`update_comparison.py
-j 1`), 100 s per benchmark, on the same machine. Nothing is committed.

## The change under test

`int.star-contains` no longer assumes nonnegative summand vectors; the
lambda predicate carries the constraints explicitly:

- cvc5 (branch liastar): ARITH_LIA_STAR_NONNEGATIVE lemma disabled and
  `setNonnegative` removed (`liastar_extension.cpp`); the pruning
  subsolver's own `>= 0` injection removed, `distribute` now seeds partial
  conjunctions with every non-OR conjunct, and both Normaliz input
  builders emit an explicit all-zero `signs` row, since Normaliz's
  constraint-only input defaults to the nonnegative orthant
  (`liastar_utils.cpp`).
- Every benchmark regenerated by `generate_benchmarks.py`: each
  star-contains lambda body now begins with `(>= v 0)` for all bound
  variables (generators: `lia_star_cvc5.py`, SQLSolver's
  `Cvc5LiaStarSolver.java`).
- 16 cvc5 regressions pass, including 5 new negative-example tests
  (`neg_*.smt2`) exercising genuinely negative summand vectors.

|---|---|---|---|---|
| cvc5 | 284 -> 284 | 199 -> 199 | 26 -> 26 | |

| unfold5 | 249 -> 249 | 180 -> 180 | 80 -> 80 | |
| unfold0 | 239 -> 237 | 168 -> 168 | 102 -> 104 | |
| no_interp | 241 -> 240 | 128 -> 128 | 140 -> 141 | |

15 per-benchmark flips in total, in three groups:

**1. The known-unstable `card/cvc5_mapa` boundary set (10 flips).** All
cvc5/SQLSolver flips are 66–100 s boundary benchmarks documented as
run-to-run unstable before this change: cvc5 trades fol_0000049
(timeout -> sat 75 s) for fol_0000071 (sat 66 s -> timeout); both SQLSolver
flavors flip fol_0000098/100 out (sat|unknown ~75 s -> timeout) and
fol_0000107/120 in (timeout -> sat|unknown|unsat 14–21 s), in lockstep —
consistent with boundary jitter, not with a semantic effect (the SQLSolver
pipeline solves with its own engine; the added conjuncts are redundant for
it).

**2. SLS-on-sql flips (5).** The SLS configurations read the *rewritten*
sql benchmarks through `smt_to_sls.py`, and the added conjuncts perturb its
translation: unfold0 loses calcite-query059 (0.7 s -> timeout) and
calcite-query193-call-4 (0.2 s -> timeout); no_interp loses
calcite-query059 and spark-query089 but *gains* calcite-query040
(timeout -> unsat 0.1 s). unfold5 is completely unchanged. These are real
effects of the benchmark rewrite on the translator's search trajectory and
deserve a look if the unfold0 sql numbers matter for the paper.

**3. cvc5: none beyond the boundary pair.** Identical counts, and every
answer that completes agrees with the baseline.

## Performance

| configuration | sum before | sum after | median before | median after |
|---|---|---|---|---|
| unfold0 | 10577 s | 10865 s | 0.162 s | 0.167 s |
| cvc5 | 2921 s | 3404 s | 0.022 s | 0.022 s |
| unfold5 | 8623 s | 8622 s | 0.263 s | 0.265 s |
| no_interp | 14176 s | 14273 s | 0.187 s | 0.183 s |
| sqlsolver | 3179 s | 2997 s | 0.017 s | 0.018 s |
| modified_sqlsolver | 3142 s | 3028 s | 0.017 s | 0.017 s |

The only systematic cost is cvc5's (+483 s, +16%): 19 `card/cvc5_bapa`
benchmarks slow down ~7x (≈3.6 s -> ≈24.6 s, answers unchanged). Cause
(established by statistics diffing, e.g. fol_0000074: 4.8k -> 58k pruning
subsolver checks): the old code injected `v >= 0` for *every* variable of
every pruning query — including the fresh skolems introduced by ite
elimination. The lambda cannot constrain those skolems, and the solver may
no longer assume their sign, so DNF-distribution pruning is genuinely
weaker. Everything else is within noise.
